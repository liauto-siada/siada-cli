# 会话压缩配置

Siada 会自动通过 LLM 生成摘要替换较旧的历史消息，保留近期对话。CLI/TUI 与 IM 共用以下触发规则，并使用当前实际生效的上下文窗口：

- **窗口不超过 500,000 tokens（含边界）：**预留 60,000 tokens，触发条件为 `已用 tokens >= max(0, 上下文窗口 - 60_000)`。
- **窗口超过 500,000 tokens：**预留窗口的 25%，在使用量达到窗口 75% 时触发。非整数阈值向上取整到下一个完整 token。

| 生效上下文窗口 | 已用 tokens 触发线 |
|---:|---:|
| 200,000 | 140,000 |
| 500,000 | 440,000 |
| 600,000 | 450,000 |
| 1,000,000 | 750,000 |

窗口不超过 60,000 tokens 时会立即达到触发条件。达到触发线不代表一定压缩：所选策略仍需有可压缩的历史，并生成非空摘要。

## 请求预算与诊断

使用 **Responses 协议**的请求，在全量本地重计后，会在现有估算余量基础上增加 **1.5 倍保守缓冲**。正常 tokenizer 路径保留原有 10% 安全余量，因此约为 `原始估算 × 1.10 × 1.5 = 原始估算 × 1.65`，结果受整数取整影响。现有 tokenizer 与 fallback 方式保持不变。例如，原全量预算 506,029 tokens 会变为 759,043，超过 1M 窗口的 750,000 触发线。

该缓冲用于补偿现有本地计数无法完整覆盖的 reasoning 与加密载荷，**不是服务端精确计数**。是否应用取决于实际计数协议，不根据 GPT 模型名称前缀猜测。它不会额外放大增量估算或服务端 usage 基线；后者已经包含缓存输入及响应用量。

MCP server schema 暂不参与本地估算与请求签名。配置 MCP server 不再强制全量重计，但签名也无法检测其 schema 变化。这是当前接受的估算限制，日志通过 `mcp_schema_counting_deferred` 明确标记；其他签名安全检查继续生效。

结构化诊断记录协议、全量／增量计数模式、缓冲前后预算、reasoning 项数量及加密载荷长度、生效窗口与分档规则、压缩结果。请求／响应对照使用服务端含缓存输入用量，不重复累加缓存。如果压缩或后续 hook 改变了已计数输入，对照会标记为不可用，避免比较不同请求。这些诊断只记录数量、长度和原因，不输出会话内容、reasoning 文本、工具参数或凭据。

## 配置方式

编辑 `~/.siada-cli/conf.yaml`：

```yaml
# 压缩策略（可选，不设置则自动选择）
compaction_strategy: null
```

## 可选值

| 策略 | 说明 | 默认适用 |
|---|---|---|
| `header_summary` | 保留首轮对话 + LLM 摘要 + 最近 30% 消息 | CLI / TUI 模式 |
| `turn_prune_summary` | 三层管线：轮次裁剪 → 工具结果截断 → LLM 摘要，保留最近 3 轮对话 | IM 模式（飞书） |

不配置时，系统根据会话模式自动选择：CLI/TUI 用 `header_summary`，IM 用 `turn_prune_summary`。

## 示例

强制 CLI 模式使用 IM 策略：

```yaml
compaction_strategy: "turn_prune_summary"
```
