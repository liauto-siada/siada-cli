# Design Document Writer

Generate design documents that are **细致（detailed）、无漏洞（no gaps）、前后一致（internally consistent）、方案确定（no ambiguity）、可执行性极高（directly implementable）、简洁无冗余（concise, no repetition）**.

---

## Execution TODO List

Before starting to write the document, first use the `todo_write` tool to generate the TODO list.

```
[ ] Phase 0 — Task Classification & Selective Clarification
    [ ] 0.1  Quick project scan (directory structure, entry points, key modules)
    [ ] 0.2  Classify task type (A / B / C)
    [ ] 0.3  If ambiguities exist that cannot be resolved by research, ask user to clarify (skip if requirements are clear)
[ ] Phase 1 — Deep Codebase Research
[ ] Phase 2 — Generate document TOC following the template in references/document-format-standard.md
[ ] Phase 3 — Section-by-Section Generation
    [ ] 3.x  Write section 1 → apply output to file
    [ ] 3.x  Write section 2 → apply output to file
    [ ] ...  (all items replaced by Phase 2 TOC; each section gets its own numbered item)
[ ] Phase 4 — Self-Review Execution (2 rounds, each targets a distinct focus area)
    [ ] 4.1  Round 1 — Completeness & Consistency：invoke run_subtask → apply fixes
    [ ] 4.2  Round 2 — Implementation Step Correctness & Conciseness：invoke run_subtask → apply fixes
    [ ] 4.3  Final consistency pass (step ordering, TOC, criterion completeness)
[ ] Phase 5 — Finalization
    [ ] 5.1  Write document to agreed output path
    [ ] 5.2  Report: issues fixed, assumptions made, items deferred
    [ ] 5.3  Ask user to review the overall document quality
```

### TODO List Execution Rules

> **Execution order**: The design document MUST be generated by strictly following this TODO list in order, top to bottom. No phase or item may be started out of order, skipped, or deferred. This list is the single source of truth for execution sequence.

> **run_subtask usage**: Phase 4 requires exactly 2 `run_subtask` invocations — one per review round (4.1–4.2), each with the shared template filled with that round's focus. The `run_subtask` in Phase 4 only returns review suggestions — all edits are applied by the main agent. In Phase 3, `run_subtask` is mandatory for any section whose expected output exceeds 200 characters; sections estimated at 200 characters or fewer may be written directly by the main agent.

> **Temp files**: All temporary files generated during execution (outlines, drafts, intermediate notes) must be stored under `~/.siada-cli/workspace/tmp/`.

## Phase 0 — Task Classification & Selective Clarification

### Step 0.1 — Quick project scan

Before classifying or asking anything, do a lightweight scan of the project to establish basic context:

```
edit_file view              # top-level directory tree
list_code_definition_names  # entry points and key packages
```

Goal: understand the project's language, framework, major modules, and rough boundaries — enough to ask informed clarification questions if needed.

### Step 0.2 — Classify the task

Identify which type this is:

| Type | Description | Key Characteristics |
|---|---|---|
| **A — Refactoring / Optimization** | Existing codebase, no functional changes | Code quality, deduplication, maintainability |
| **B — Feature Development / Iteration** | Existing codebase, new or changed behavior | New APIs, data model changes, integration points |
| **C — New Project / From Scratch** | No existing codebase | Architecture, tech stack, data model, API design |

### Step 0.3 — Selective clarification before research

**Only ask if ambiguities exist that cannot be resolved by reading the codebase or context.** If the request is sufficiently clear, skip this step and proceed directly to Phase 1.

When clarification is needed, focus only on blockers — questions whose answers would materially change the research scope or design direction. Typical examples:

- **Task scope**: Which modules/files are in scope when multiple interpretations are possible?
- **Non-goals**: Is there anything that must NOT change that isn't obvious?
- **Constraints**: Are there tech stack or deployment constraints not visible in the codebase?
- **Output location**: Where should the design doc be written? (default: `<project>/design-docs/<topic>.md`)

> **Rule**: Ask only what you cannot infer. Do not ask for information that codebase research can answer. Batch all questions into a single message if multiple are needed.

> **Interaction rule**: Phase 0 is the ONLY place to ask clarifying questions before the document is complete. Once research begins (Phase 1), proceed autonomously through Phase 4 without asking the user anything.

## Phase 1 — Deep Codebase Research

Execute systematically. Do NOT start writing the document until research is complete.

### 1.1 — Map the codebase structure

```
list_code_definition_names   # top-level and each relevant package
edit_file view               # directory trees
```

Build a mental map:
- Package structure and layer boundaries
- Entry points (main classes, controllers, pipelines)
- Core interfaces and their implementations
- Configuration and wiring (Spring beans, constructors, DI)

### 1.2 — Read ALL files relevant to the task scope

**Type A (Refactoring):** Read every file that contains the duplicated/problematic patterns. Do not rely on grep alone — read full file contents for any file that will be modified.

**Type B (Feature):** Read:
- All files the new feature will touch (modify or extend)
- All files that define the interfaces/contracts the feature must conform to
- Test files for the affected area (understand expected behavior)
- Configuration files (application.yml, etc.)

**Type C (New Project):** Read any reference materials the user provides (requirements docs, API specs, similar projects).

### 1.3 — Record findings while reading

For each file read, note and **append to `~/.siada-cli/workspace/tmp/research-findings.md`**:
- What it does
- What it DOESN'T do (important for Type A — dead code, unused paths)
- How it connects to other components
- Any patterns, conventions, naming styles to follow

> Save findings to file incrementally as you read — do not rely on in-context memory. This file will be read by `run_subtask` invocations in Phase 3.

### 1.4 — Verify all assumptions

Before writing, explicitly confirm:
- Every class/method you plan to reference actually exists (check exact names)
- Every new type you plan to introduce doesn't already exist elsewhere
- Package names and visibility rules are correct
- No circular dependencies would be introduced

## Phase 2 — Generate document TOC

Generate the document Table of Contents following the template in `references/document-format-standard.md`. Proceed directly without waiting for user input.

- Use three-level numeric headings: `1.`, `1.1`, `1.1.1`
- The last chapter must always be `N. 实施步骤`
- Write the TOC directly to the final design document file as the first content after the header block
- For each section in the TOC, also write a **section brief** to `~/.siada-cli/workspace/tmp/section-briefs.md` — one entry per section with: section number, title, and 3–5 bullet points describing the key content to cover. This file is the primary input for Phase 3 `run_subtask` invocations.
- After writing, **update the TODO list file** with Phase 3 items expanded from the TOC — one item per section

## Phase 3 — Section-by-Section Generation

Before writing each section, estimate its expected output length. If the estimate exceeds 200 characters, the section **must** be written by invoking `run_subtask`. Sections estimated at 200 characters or fewer may be written directly by the main agent. The main agent is responsible for applying all output to the document file.

### `run_subtask` instruction template (per section)

For each section, construct a `run_subtask` instruction containing all of the following:

```
You are writing one section of a design document. Do not write any other section.

## Your task
Write section: <section title and number>

## Document context
- Document path: <absolute path to the design document file>
- Document goal: <one-sentence goal from header block>
- Project directory: <absolute path to the project root>
- Full TOC: <paste the TOC already written in the design document>

## Section brief
<paste the entry for this section from ~/.siada-cli/workspace/tmp/section-briefs.md — section number, title, and key content points>

## Research findings (relevant to this section)
<read ~/.siada-cli/workspace/tmp/research-findings.md and paste the entries relevant to this section>
<further codebase exploration is allowed and generally recommended — read additional files, grep for usages, or trace call chains as needed to write this section with full accuracy>

## Previously written sections (for consistency)
<brief summary of each section written so far — key decisions, conclusions, and named entities (classes, methods, fields) introduced>

## Section format requirements
<paste the relevant format rules from the Document Format Standard below>

## Output
Return ONLY the markdown content for this section. Write it with maximum detail and completeness — the output must faithfully reflect every point captured in the outline entry above. Do not include any preamble, explanation, or content from other sections.
```

### Document Format Standard

See `references/document-format-standard.md` for the canonical template.

Key invariants that must hold in every document:

**Header block (always first):**
```markdown
# <Project/Module> <Task Type> 设计文档

> 目标：<one clear sentence — what changes and why>
> 范围：<files/modules in scope; explicitly state out-of-scope items>
```

**Table of Contents (always second, REQUIRED):**
- Use three-level numeric headings: `1.`, `1.1`, `1.1.1`
- List every `##` and `###` section with anchor links
- The last entry must always be `N. 实施步骤` with its steps listed as `N.1`, `N.2`, ...

**Analysis chapters (1 through N-1):**
- Chapter titles follow numeric scheme: `## 1. <Title>`, `### 1.1 <Title>`, `#### 1.1.1 <Title>`
- Content is task-specific — no fixed structure required; choose what best serves the design
- Each problem/requirement should have a unique numeric ID (e.g., `2.1`, `3.2`) for cross-referencing in implementation steps

**Implementation Steps (final chapter, REQUIRED):**
- Always the last chapter, titled `## N. 实施步骤`
- Steps are numbered `### N.1 Step 1：...`, `### N.2 Step 2：...`
- Each step MUST include a `**验收标准：**` block with measurable, observable criteria
- Steps must be in dependency order (Step N must not assume anything delivered by Step N+1)
- Steps that have NO dependencies on each other may be marked as independently executable

### Main agent responsibility after each `run_subtask` completes

1. Read the `run_subtask` output
2. Apply it to the document file (append the section)
3. Verify the written content is consistent with all previous sections
4. If an inconsistency is found, correct it directly before invoking the next `run_subtask`

## Phase 4 — Self-Review Execution

This phase is **mandatory** — exactly **2 review rounds** must be completed in sequence, each targeting a distinct focus area. Do not skip, merge, or reorder rounds under any circumstances.

Each round **must** be conducted by invoking `run_subtask`. The purpose is review independence: a fresh context with no prior writing bias catches issues the main agent overlooks. **Even if you are highly confident in the document quality, you must invoke `run_subtask` for every round.** The `run_subtask` is responsible for both finding issues and fixing them directly in the document file. After all fixes are applied, it must report what issues were found and what changes were made.

### `run_subtask` instruction template (shared across all rounds)

Construct each round's instruction from this template. The only part that changes between rounds is the `## Review focus` block — fill it with the focus defined in the corresponding sub-section below.

```
You are independently reviewing a design document. Your only output is a numbered list of review issues.

## Context
- Project directory: <absolute path to the project root>
- Design document path: <absolute path to the design document file>

## Your responsibilities
1. Read the design document in full by reading the file at the document path above — do not skim or skip any section.
2. Actively explore the codebase to verify claims in the document: read source files, trace call chains, grep for usages, check configs. Do not trust the document's description of code — confirm it yourself. The more code you read, the more issues you will catch.
3. Only after thoroughly reading the document AND exploring the codebase, identify all issues within the review focus.
4. Fix every issue directly in the document file. Do not leave any identified issue unfixed.
5. After all fixes are applied, produce the output report below.

## Review focus
<Paste the focus table for this round — see the corresponding sub-section in Phase 4>

## Output format
Return a structured report with two sections:

**Issues found:** numbered list of issues. Each issue must include:
- The specific location (section/step number or heading)
- The exact problem found

**Changes made:** numbered list of edits applied to the document, each describing what was changed and where.

If no issues are found, return: "No issues found."
```

**After each round completes:** read the report returned by `run_subtask` (issues found + changes made). The `run_subtask` has already applied all fixes — do not re-apply them. If any reported fix required an assumption, record it for the Phase 5 report. **Only mark a round's TODO item `✅` after the `run_subtask` has returned and its report has been reviewed** — never update the TODO list in advance.

---

### 4.1 — Round 1: Completeness & Consistency

Focus on whether the document covers everything it must and is internally consistent.

| Category | What to check |
|---|---|
| Gap detection | Are there scenarios, edge cases, or failure modes the design does not address? |
| Better alternatives | For each key design decision, is the chosen approach clearly justified? Could a simpler or more robust alternative have been overlooked? |
| Acceptance criteria completeness | Each criterion is measurable; the full set covers every item in the change list |
| Behavior changes | Every behavior change (not just structural) is explicitly called out with a warning |
| Analysis-to-step coverage | Every problem/requirement identified in analysis chapters maps to at least one implementation step |
| No missing steps | No change mentioned in the document lacks a corresponding step in 实施步骤 |
| Naming consistency | Same concept uses the same name throughout (class names, field names, terminology) |
| Ambiguity | No sentence contains "可以" / "or" / "optional" without a resolved decision |
| Internal cross-references | All section numbers and step numbers cited within the document are correct |
| Contradictions | No two sections make conflicting claims about the same behavior or design decision |

---

### 4.2 — Round 2: Implementation Step Correctness & Conciseness

Focus on whether the implementation steps are correct and safely executable, and that every sentence earns its place.

| Category | What to check |
|---|---|
| Cross-step references | Every class/method referenced in Step N either already exists or is created in a prior step |
| Type visibility | New types/methods have correct access modifiers for all their callsites |
| Step ordering | No step assumes outputs from a later step |
| Dead code safety | Before deleting anything, confirmed no live callsites exist (including tests, configs, XML) |
| Specific descriptions | No vague change descriptions ("refactor X to be cleaner") — every change specifies exact file, method, and what changes |
| TOC accuracy | TOC lists every `##` and `###` section with correct numeric labels matching the document body |

---

### 4.3 — Final consistency pass (main agent only, no `run_subtask`)

After all 2 rounds and their fixes are applied, perform a final structural check directly:

- Step N.1 through Step N.M: verify the dependency chain is correct
- Verify every step heading (`### N.x Step ...`) has `**当前状态：**` (immediately after 目的) and `**验收标准：**` blocks
- Verify `实施步骤` is the last chapter
- Verify the TOC is fully up to date with the final document structure

---

## Phase 5 — Finalization

1. Write the document to the agreed output path
2. Report to the user:
   - How many issues were found and fixed during self-review
   - Any decisions that required assumptions (list them explicitly)
   - Any items explicitly deferred or out of scope
3. **Ask the user to review the overall document quality** — this is the only user interaction after Phase 0. Invite the user to read the document and share any feedback on structure, completeness, accuracy, or missing content.
4. Delete all temporary files created during execution under `~/.siada-cli/workspace/tmp/` (including `research-findings.md`, `section-briefs.md`and so on.).

## Rules & Anti-Patterns

### MUST DO
- **Read before write**: Never describe what code does without having read it
- **Name exactly**: Use the exact class/method/field names as they appear in source
- **Decide, don't hedge**: Pick one approach and state why; never say "either X or Y works"
- **Acceptance criteria = observable**: Each criterion must be verifiable by running code, checking output, or inspecting diffs — never "code looks clean"

### MUST NOT
- Do not write placeholder sections ("TBD", "see design doc", "details to follow")
- Do not use vague change descriptions ("refactor X to be cleaner") — always specify exact file, method, and what changes
- Do not reference types that don't exist yet without specifying in which prior step they get created
- Do not assume the user knows what you mean — if a term is ambiguous, define it on first use
- Do not add optional/nice-to-have items to the implementation steps — those go in a separate "Future Considerations" section at the end
- Do not use code to express design — all behavior, structure, design decisions, and change descriptions must be written in natural language; code blocks are permitted only for command-line invocations or configuration snippets where prose would be genuinely ambiguous; do not use code blocks as a substitute for design thinking

## Quick Reference: When to Ask vs. When to Decide

> **Hard rule**: Questions to the user are only permitted in Phase 0 (before research) and Phase 5 (after the document is written). Never ask the user anything during Phases 1–4.

| Situation | Phase 0 action | Mid-process (Phases 1–4) action |
|---|---|---|
| Scope boundary unclear | **Ask** if not inferable from codebase | Infer from context; flag assumption in Phase 5 report |
| Two approaches with different tradeoffs | Ask if blocking; otherwise decide in doc | Decide autonomously; document rationale |
| Behavior change affecting external interfaces | Ask if critical to scope decision | Document it clearly; flag in Phase 5 report |
| Internal refactoring, no behavior change | Not needed | Decide autonomously |
| Naming for new internal classes/methods | Not needed | Decide, document the name, move on |
| Output location unknown | Ask (default: `design-docs/<topic>.md`) | N/A/ |
