## 一、背景与问题

当前 siada 对单次可完成的编程任务效果良好，但面对复杂任务时能力明显不足。核心问题不是执行能力，而是**方向漂移**：agent 在长周期执行过程中逐渐偏离正确路径，无法维持对任务全局的一致理解。

具体表现：对于复杂任务，agent 的实现结果往往不符合预期——执行方向在过程中发生漂移，最终产出偏离了用户的真实意图。

**核心洞察**：只要问题被足够清晰地规格化，agent 就有能力自主完成。设计文档就是这个规格化的载体。

---

## 二、设计目标

1. 让 agent 能够完成符合预期的长周期编程任务

## 三、核心机制与工作流程

### 3.1 核心机制
1. design-driven-vibecoding为核心理念。在真正开始编码之前尽可能完善设计文档，让Agent遵循设计文档编码。
   - 这里的design指的是技术设计文档。
2. 设计文档的编写由Agent和人类共同完成，
   - Agent为设计文档的主要编写者
   - 人类需要为Agent提供设计文档的主要编写方向并review编写过程
   - Agent需要“督促”工程师对长周期任务编写设计文档，帮助工程师想清楚逻辑
3. 不是所有的任务都需要编写设计文档，Agent需要根据任务的复杂度来判断是否需要设计文档。 
   - 复杂度判断的条件：需要修改大量代码， 需要补充大量指令外的信息，有大量需要澄清的内容。
4. 设计文档的编写流程和规范放在skill中， 只有Agent认为需要编写设计文档时，才加载skill 内容 （其实也不一定用skill，因为要在主agent中提示在固定场景下使用此skill, 有了这个提示，直接只是读文档也行）：
   - 文档编写过程中允许向用户提除关于需求澄清类的问题， 但是问题必须有价值， 不能为了提问而提问
   - skill 中包含设计文档模版的地址， 按此模版生成文档。
   - 实现设计文档后必须检查文档内是否有自相矛盾的地方、是否有重大漏洞
   - 用户确认文档后，指示按照设计文档生成代码，并提示更新进度。
5. 长周期任务执行skill， 对于设计文档完善的任务， 加载长周期任务执行skill. skill 内容：
   - 从设计文档中提取执行步骤， 列为todo list, 规定展示 todo list 的格式。
   - 规定每个todo 项使用子 agent 执行，主agent负责收集执行结果，并更新当前进展， 启动下个子任务。
   - 为什么要用子agent执行子任务， 
     - 为了保证每个子任务都有和本身任务最相关的上下文执行窗口，不会因为窗口中遗留了过多上个任务的内容而影响此任务的质量， 每个任务的执行过程都是小而精的。而且也不是完全丢失了上个任务的执行过程， 父agent会将设计文档、当前进展、上个任务的执行结果传递给子agent。
     - 设计完善的任务理论上不需要用户澄清，有子agent静默执行就可以了。（但是可能需要给用户展示大概的执行内容， 避免用户以为卡住了， 但是这里的交互过程还需要设计一下）
6. 增加子任务执行系统。
   - 对于每个子任务都有一个单独的code_gen_agent的子类执行， 使用改良版的系统提示词：增加类似不需要用户提示之类的规则。
   - 给父agent增加子任务工具，负责调起子agent执行， 工具文档中规定只有指令中明确规定需要使用此工具，才可以使用此工具。
   - 子agent组要增加返回内容工具：包括当前进展，子任务完成总结。 用于前端进度的展示。
   - 子agent执行的输入是设计文档路径以及执行具体步骤提示。

### 3.2 整体流程

```
用户提交任务
     │
     ▼
┌─────────────────────────────┐
│  复杂度判断                  │
│  Agent 自评任务是否复杂       │
└─────────────────────────────┘
     │                    │
  简单任务               复杂任务
     │                    │
     ▼                    ▼
  直接执行         加载设计文档生成 Skill
  （正常流程）             │
                          ▼
                  向用户提问澄清（必要时）
                          │
                          ▼
                  Agent 生成设计文档
                  保存至 design_docs/<task>.md
                          │
                          ▼
                  文档自检
                  （无矛盾 / 无漏洞 / 无待确认）
                          │
                          ▼
                  向用户展示文档，等待确认
                          │
               ┌──────────┴──────────┐
            确认通过               需要修改
               │                    │
               │              用户反馈 → 修改文档
               │                    │
               └──────────┬─────────┘
                          │
                          ▼
                  加载长周期任务执行 Skill
                          │
                          ▼
                  从设计文档提取实现步骤
                  生成 Todo List，展示给用户
                          │
                          ▼
              ┌───────────────────────────┐
              │  主 Agent 循环执行各步骤    │
              │                           │
              │  1. 启动子 Agent           │
              │     instruction=当前步骤   │
              │     context=Skill 格式化   │
              │  2. 子 Agent 静默执行      │
              │  3. 子 Agent 返回执行摘要  │
              │  4. 主 Agent 更新步骤状态  │
              │     （未实现 → 已完成）     │
              │  5. 展示当前进度           │
              │  6. 启动下一步骤           │
              └───────────────────────────┘
                          │
                     所有步骤完成
                          │
                          ▼
                     任务结束
```

**关键节点说明：**

**复杂度判断**：Agent 自主评估，无需用户介入。判断结果直接决定走哪条路径，不打断用户。详见 3.3。

**设计文档生成**：Agent 驱动，人类配合。Agent 是主笔，负责把需求转化为完整的技术设计文档；用户负责方向引导和最终确认。确认前 Agent 不进入执行阶段。

**人工确认门**（Confirmation Gate）：整个流程中唯一强制的人工介入点。文档确认后，执行阶段完全由 Agent 自主推进，不再要求用户响应。

**子 Agent 执行循环**：每个步骤独立启动一个子 Agent，子 Agent 拥有干净的上下文窗口（仅包含设计文档 + 本步骤指令），避免历史执行内容干扰当前任务质量。主 Agent 负责串联各步骤、维护进度。

**进度可见性**：虽然执行阶段无需用户操作，但每个步骤完成后主 Agent 会更新设计文档中的步骤状态并向用户展示，让用户始终了解当前进展，避免任务"静默运行"带来的困惑。

**会话中断恢复**：若任务中途中断，恢复时 Agent 读取设计文档中各步骤状态，找到第一个未完成的步骤，从该步骤继续执行。恢复逻辑无需独立状态文件，完全依赖设计文档本身。

### 3.3 复杂度判断

复杂度判断由 Agent 在接收任务后立即自主完成，无需询问用户，结果直接决定走设计文档路径还是直接执行路径。

#### 判断维度

Agent 从以下三个维度综合评估：

| 维度 | 说明 | 触发信号 |
|------|------|----------|
| **代码改动范围** | 任务需要跨多个模块/文件进行修改，单次对话难以完整覆盖 | 涉及文件数量多、需要新增多个模块、改动会影响多处调用方 |
| **信息缺口** | 指令本身信息不足，必须补充大量背景才能正确实现 | 架构背景不明、依赖关系不清、需要做大量技术选型决策 |
| **需求模糊度** | 需求存在多个合理解读方向，或有大量实现细节未定义 | 关键行为未说明、边界条件模糊、存在多种可行方案需要取舍 |

#### 判断位置与透明度

- 判断在收到任务后、任何执行行为之前完成
- 若判定为复杂任务，Agent 应向用户简短说明判断依据，例如：
  > "这个任务涉及多个模块改动且需求有待澄清，我会先生成一份设计文档，请确认后再开始执行。"
- 判断本身不阻塞流程，用户无需显式批准

### 3.4 生成设计文档 Skill 设计

#### 触发时机

复杂度判断结果为"复杂任务"时，Agent 加载本 Skill。Skill 以文档形式存储，Agent 读取后按其中规范执行，不作为独立进程运行。

#### 工作流程

```
加载 Skill
    │
    ▼
收集上下文（读取代码库、已有文档等）
    │
    ▼
识别信息缺口 → 必要时向用户提问（见澄清规范）
    │
    ▼
按模版生成设计文档，保存至 design_docs/<task-slug>.md
    │
    ▼
文档自检（见自检规范）
    │
    ▼
向用户展示文档摘要，请求确认
    │
    ▼
用户确认 → 转入执行阶段
用户要求修改 → 修改文档 → 重新自检 → 再次请求确认
```

#### 澄清提问规范

- 只在**无法通过读取代码库或已有文档自行推断**时才提问
- 单次提问应将所有必要问题**合并为一次**，不允许多轮单个追问
- 每个问题必须说明"为什么需要这个信息"，帮助用户理解价值
- 禁止提问可以合理假设的内容（如命名风格、日志级别等细节）

#### 文档生成规范

- 文档路径：`design_docs/<task-slug>.md`，slug 由任务标题派生，使用小写连字符格式
- 文档结构严格遵循第四章《设计文档规范》中的必要字段
- 技术设计部分需覆盖：模块划分、接口设计、数据流、关键决策及理由
- 实现步骤须拆分至**单个子 Agent 可独立执行**的粒度，每步附验收标准

#### 自检规范

文档生成后，Agent 必须对文档进行以下三项检查，任意一项不通过则修改后再提交：

| 检查项 | 通过标准 |
|--------|----------|
| 无自相矛盾 | 各章节对同一概念/行为的描述一致，无逻辑冲突 |
| 无重大漏洞 | 实现步骤可以完整覆盖技术设计，没有明显遗漏的环节 |
| 无待确认内容 | 文档中不存在"待定"、"TBD"、"需确认"等未决项 |

#### 确认与收尾

- 向用户展示时只需展示**文档摘要**（目标、技术方案概述、步骤列表），完整文档路径附后
- 用户确认后：直接指示主 Agent 进入执行阶段，传递设计文档路径

### 3.5 执行复杂任务 Skill 设计

#### 触发时机

用户确认设计文档、上下文清空完成后，主 Agent 加载本 Skill。输入为设计文档路径。

#### Todo List 格式

Agent 从设计文档的"实现步骤"章节提取步骤，生成 Todo List 并展示给用户：

```
## 执行计划

[ ] 步骤 1：<步骤标题>
[ ] 步骤 2：<步骤标题>
[x] 步骤 3：<步骤标题>（已完成）
...

当前进度：1 / N 已完成
```

展示后无需用户确认，主 Agent 立即开始执行。

#### 主 Agent 循环逻辑

主 Agent 按以下循环推进任务，直到所有步骤完成：

```
取出下一个状态为"未实现"的步骤
    │
    ▼
调用 run_subtask 工具，启动子 Agent
    instruction=设计文档路径 + 上一步骤完成摘要 + 下一步动作指示
    context=""（空）
    │
    ▼
等待子 Agent 返回执行摘要
    │
    ▼
成功：将步骤状态更新为"已完成"，写入执行摘要，更新设计文档
失败：步骤状态保持"未实现"，通知用户，等待指示
    │
    ▼
向用户展示更新后的 Todo List（当前进度）
    │
    ▼
是否还有未实现步骤？
    ├── 是 → 继续循环
    └── 否 → 向用户输出任务完成总结
```

#### 子 Agent 执行规范

- 每个子 Agent 拥有独立、干净的上下文窗口，不继承主 Agent 的历史对话
- 子 Agent 的输入严格限定为：
  1. `instruction`：当前步骤的具体执行指令
  2. `context`（可选）：Skill 负责格式化并注入，在 long-horizon 场景中包含设计文档路径和已完成步骤摘要
- 子 Agent 使用改良版系统提示词，关键差异：
  - 不向用户请求确认，遇到歧义优先参考设计文档，仍无法决策时才上报主 Agent
  - 执行结束时输出符合 `SubTaskResult` 结构的结果（由 `output_type` 强制保证）
- 子任务工具的工具说明中注明：**只有主 Agent 指令中明确要求时才可调用**，防止滥用

#### 子 Agent 返回结构

```json
{
  "step": "<步骤标题>",
  "status": "completed | failed | blocked",
  "summary": "<本步骤执行了什么、修改了哪些文件、关键决策>",
  "blockers": "<仅 blocked 时填写：阻塞原因及建议>"
}
```

- `completed`：主 Agent 正常推进下一步
- 其他（`failed` / `blocked`）：统一视为失败，主 Agent 通知用户并等待指示

#### 中断恢复

任务中断后重新启动时：

1. 用户提交恢复指令（或 Agent 检测到未完成的设计文档）
2. Agent 读取设计文档中各步骤状态
3. 找到第一个状态为"未实现"的步骤，从该步骤继续
4. 向用户展示当前 Todo List 状态，说明从哪一步恢复

### 3.6 子任务执行系统设计

3.5 描述的是 Skill 层面的行为规范，3.6 描述的是支撑这些行为的**系统实现**：子 Agent 的类结构、工具接口定义，以及两侧的调用约定。

> **设计原则**：`SubTaskAgent` 和 `run_subtask` 是**通用基础设施**，不与 long-horizon 场景耦合。long-horizon 是首个使用方，但该机制同样适用于其他需要以干净上下文独立执行子任务的场景。工具签名只负责"启动子 Agent 执行一个任务"，输入的具体格式由调用方（Skill 或主 Agent 指令）负责组装，工具本身不关心业务语义。

#### 子 Agent 实现

`SubTaskAgent` 继承自 `CodeGenAgent`，执行方式与父类完全一致：通过 `Runner.run()` 驱动，使用同一套 `RunConfig` / provider 体系，不引入新的执行基础设施。

**执行流程：**

```
run_subtask 工具被调用
    │
    ▼
从当前 context var 读取 LLM_CONFIG
    │
    ▼
调用 get_provider(llm_config.provider) 获取 provider 实例
    │
    ▼
构造 RunConfig（model / model_provider / model_settings）
    │
    ▼
构造 CodeAgentContext(root_dir=workspace)
    │
    ▼
拼装输入（instruction=当前步骤指令, context=调用方格式化的上下文）
    │
    ▼
await Runner.run(
    starting_agent=SubTaskAgent(),
    input=assembled_input,
    context=agent_context,
    run_config=run_config,
)
    │
    ▼
子 Agent 调用 report_result → run_subtask 返回结果
```

**provider 固定策略：**

子 Agent 不独立解析 provider，而是直接继承主 Agent 当前会话的 `LLM_CONFIG` context var。这确保主子 Agent 始终使用同一个 provider 和 model，不会因为 provider 差异产生行为不一致。`RunConfig` 的构建方式与 `SiadaRunner._build_run_config()` 完全对齐：

```python
llm_config = get_context_var(LLM_CONFIG)          # 继承自主 Agent 会话
model_provider = get_provider(llm_config.provider) # 相同 provider
provider_wrapper = ModelProviderWrapper(
    base_provider=model_provider,
    input_processor=process_input,
)
run_config = RunConfig(
    model=llm_config.model_name,
    model_provider=provider_wrapper,
    model_settings=ModelSettingsConverter.convert_model_settings(llm_config),
    tracing_disabled=...,
)
```

**系统提示词与标准版的关键差异：**

| 项目 | 标准 CodeGenAgent | SubTaskAgent |
|------|-------------------|--------------|
| 用户确认 | 执行前可向用户请求确认 | **禁止**主动向用户发起提问或确认 |
| 歧义处理 | 询问用户 | 优先参考设计文档；仍无法决策时在最终输出中返回 `blocked` 状态 |
| 输出类型 | 自由文本 | `output_type=SubTaskResult`，SDK 强制最终输出为结构化结果 |
| 工具集 | 完整工具集 | 仅注册当前步骤所需的工具 |
| 上下文来源 | 完整历史对话 | 仅限调用方注入的 `instruction` |

**启动时注入的输入：**

- `instruction`：子任务的完整输入字符串；调用方负责将设计文档路径、上一步骤完成摘要、当前步骤指令按固定模板拼装后传入

#### 子任务工具（主 Agent 侧）

主 Agent 持有 `run_subtask` 工具，是启动子 Agent 的唯一入口。

**工具说明（写入工具 docstring，供 LLM 读取）：**

> 在独立上下文中启动一个子 Agent 执行指定任务。**仅当当前指令中明确要求使用本工具时才可调用**，禁止自行判断调用时机。

**工具签名：**

```python
def run_subtask(
    instruction: str,    # 子任务的完整输入；调用方负责将设计文档路径、
                         # 上一步骤摘要、当前步骤指令拼装为统一字符串
) -> SubTaskResult:
    ...
```

**行为约定：**

- 同步阻塞，等待子 Agent 执行完毕后返回
- `Runner.run()` 返回后，从 `result.final_output` 直接读取 `SubTaskResult`，无需额外解析
- 拿到结果后向前端推送步骤状态变更，触发 Todo List 更新

#### 结构化输出（子 Agent 侧）

`SubTaskAgent` 声明 `output_type=SubTaskResult`，Agents SDK 强制最终输出符合此结构，无需额外工具或信号机制。

**输出类型定义：**

```python
class SubTaskResult(BaseModel):
    status: Literal["completed", "failed", "blocked"]
    summary: str        # 执行了什么、修改了哪些文件、关键决策
    blockers: str = ""  # 仅 blocked 时填写：阻塞原因及建议
```

**状态语义：**

| 状态 | 含义 | 主 Agent 后续动作 |
|------|------|------------------|
| `completed` | 步骤正常完成 | 更新文档状态为已完成，推进下一步 |
| `failed` | 发生不可恢复的错误 | 记录失败原因，暂停并通知用户 |
| `blocked` | 遇到设计文档未覆盖的决策点 | 将 `blockers` 传达给用户，收到回复后重新启动该步骤 |

**为何不用工具**：`output_type` 由 SDK 层强制保证，比要求 Agent 主动调用工具更可靠，且不需要异步信号机制或兜底 fallback 逻辑。

## 四、设计文档规范

### 4.1 必要字段

1. 需求概要与目标
   - 背景是什么
   - 需要实现什么功能
   - 达到什么目标
2. 技术设计
3. 实现步骤
   - 是技术设计的详细实现计划
   - 每一步要有执行状态：未实现、实现中、已完成
   - 每一步要有验收标准
     - 可以是测试用例
     - 也可以是别的内容：例如验证命令或检查项


### 4.2 文档质量标准
- 无自相矛盾之处
- 无重大漏洞
- 无待确认内容
